# 31. OIO 캐스팅 통합 플랫폼 구상 — 이용자 + 직원(사내) 한 플랫폼 (2026-11-16, 검토용 초안)

## 1. 내가 이해한 전체 사이클 (틀린 곳을 고쳐 주세요)

### 1-1. 세 종류의 사용자
| 구분 | 누구 | 하는 일 |
|---|---|---|
| **이용자** (공개 영역) | 출연자 — 보조출연·단역·이미지단역·외국인단역·외국인출연자 | 가입 → **프로필 등록**(사진 등) → 공고 **조회** → **신청** → 합격 통보 → **확정**, **취소**(사유 작성) |
| **직원** (OIO 소속, 직원용 영역) | 대표·이사·실장(추정)·스케줄러·현장 팀장·일반 직원 | 촬영 일정·필요 인원 관리, 공고 게시, 선발, 현장 운영. **직급별로 작성·수정 가능 범위가 다르다** |
| **총괄 관리자** (개발자) | 개발 담당 | 모든 것을 수정·삭제할 수 있음. 직원 계정·직급·설정·삭제(복구 포함) 최종 권한 |

첫 화면에서 "이용자로 시작" / "직원 로그인"으로 갈라진다.

### 1-2. 한 사이클 (촬영 한 건 기준)
1. **촬영 일정 등록** — 대표·스케줄러가 OIO 의 현재 촬영(작품·날짜·장소·시간)을 등록한다.
2. **일정별 필요 인원 등록** — 날짜마다 "어떤 유형의 인원이 몇 명 필요한지"(예: 보조출연 30, 외국인단역 2)를 적는다.
3. **공고 게시 = 일정 등록의 결과** — 따로 공고를 또 쓰지 않고, 등록·수정한 내용이 **바로 이용자에게 보인다**. 수정도 즉시 반영.
4. **이용자 신청** — 이용자가 공고(날짜·역할)를 보고 신청한다(신청 사유 작성 가능).
5. **확정** — 직원이 신청자를 보고 선발·확정하면 인원이 채워진다. (기존 설계: 합격 통보 → 이용자 확정의 2단계)
6. **팀장 배정** — 다른 팀장들은 일정을 보고 **스스로 팀장 등록**할 수 있고, 실장 이상은 **팀장을 등록·배정**할 수 있다. 팀장 등록·취소에도 사유를 쓴다.
7. **취소** — 이용자의 신청 취소, 팀장의 팀장 등록 취소 모두 **사유 필수/작성 가능**.
8. (이후) 현장 출석·인원표·메시지 등은 기존 기능을 재사용.

### 1-3. 내가 가정한 것 (확인 필요)
- "싱장"은 **실장**으로 읽었다. 직급 서열은 `총괄 > 대표 > 이사 > 실장 > (기능직) 스케줄러 · 현장 팀장 > 직원` 으로 가정.
- 스케줄러는 직급이 아니라 **기능 역할**(촬영 일정을 다루는 사람)로 본다. 이사도 일정 등록이 가능하다고 가정.
- OIO **한 회사만** 쓴다(여러 업체가 가입하는 구조 아님). 다만 코드의 다중 업체 구조는 지우지 않고 OIO 1개만 사용하는 방식을 권한다(§4-1).

### 3-3. 비교에서 얻은 결론
1. **국내 경쟁은 "보조출연 일당 매칭"이 중심**이고, OIO 처럼 **단역·이미지단역·외국인까지 한 회사가 직접 캐스팅**하는 내부 업무 도구는 공개 자료에서 찾지 못했다. 차별점은 "공개 모집 + 사내 운영 도구를 한 DB 로 잇는 것"이다.
2. 해외는 **프로필(공개) ↔ 캐스팅 담당자 도구(내부)**가 한 플랫폼의 두 얼굴이다. 우리 구조(이용자 영역/직원 영역)와 맞다.
3. 유형별로 요구가 다르다: 보조출연=인원·시간·간격, 단역·이미지단역=사진·포트폴리오·오디션형, 외국인=서류·언어·체류자격. **유형별 프로필·요건이 이 플랫폼의 핵심 설계 포인트**다.

## 4. 구상

### 4-1. 큰 구조
```
첫 화면
 ├─ 이용자로 시작 ──▶ 출연자 앱(Flutter, 앱+웹)  : 가입·프로필·공고 조회·신청·확정·취소
 └─ 직원 로그인   ──▶ 직원 웹(React)               : 촬영·일정·필요 인원·공고·선발·팀장·현장·메시지
총괄(개발자)       ──▶ 직원 웹 안의 "총괄" 메뉴       : 계정·직급·권한·설정·삭제/복구·감사로그
```
- 데이터베이스·서버는 하나. 직원 영역은 OIO 회사 1개에 묶는다(기존 `companies` 테이블 재사용, OIO 를 미리 등록·승인 상태로 시드). **다른 업체 가입 화면은 숨긴다**(코드 삭제는 하지 않음 — 나중에 파트너 업체를 열 수도 있어서).
- 직원 계정은 가입이 아니라 **대표·총괄이 초대/생성**하고, 첫 로그인에서 비밀번호를 정한다.

### 4-2. 직급·권한 (제안 — 표로 정하고 DB 에서 바꿀 수 있게)
**직급 서열**(위가 높음): 총괄 > 대표 > 이사 > 실장 > 현장 팀장 > 직원. **스케줄러**는 직급에 더해 붙는 기능 권한.

| 기능 | 총괄 | 대표 | 이사 | 실장 | 스케줄러 | 팀장 | 직원 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| 촬영·일정·필요 인원 등록/수정 → 공고 즉시 반영 | ✔ | ✔ | ✔(가정) | ✖ | ✔ | ✖ | ✖ |
| 일정·공고 열람 | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ |
| 이용자 신청 열람·선발(합격 통보) | ✔ | ✔ | ✔ | 질문 | ✔ | 열람 | ✖ |
| **팀장 스스로 등록/취소(사유)** | ✔ | ✔ | ✔ | ✔ | ✖ | ✔ | ✖ |
| **팀장 등록·배정·해제(타인)** | ✔ | ✔ | ✔ | ✔ | ✖ | ✖ | ✖ |
| 직원 계정 초대·직급 변경 | ✔ | ✔ | 실장 이하 | ✖ | ✖ | ✖ | ✖ |
| 개인정보(주민/외국인등록번호·계좌) 전체 열람 | ✔ | ✔ | 질문 | ✖ | ✖ | ✖ | ✖ |
| 삭제 | ✔ | 취소·숨김만 | 취소·숨김만 | ✖ | ✖ | ✖ | ✖ |
| 설정·감사 로그 | ✔ | 열람 | ✖ | ✖ | ✖ | ✖ | ✖ |

구현 방식: 지금처럼 코드에 직책 이름을 박지 않고, 이미 있는 `roles`·`permissions`·`role_permissions` 테이블에 "권한 항목(예: `SCHEDULE_WRITE`, `LEADER_ASSIGN`)"을 넣고 직급마다 묶는다. 그러면 대표·총괄이 화면에서 권한을 조정할 수 있다. 모든 변경은 감사 로그.

| 단역 | 대사/연기 가능, 오디션형 가능 | + 경력·출연 영상/링크·소속 여부 |
| 이미지단역 | 외모·분위기·체형(콘셉트) | + 전신·반신 사진 다수, 의상 사이즈, 스타일 태그 |
| 외국인단역 | 외국인 + 단역 | + 국적·구사 언어·**체류자격**·외국인등록증 확인 |
| 외국인출연자 | 외국인 + 비중 있는 출연 | 위와 같음 + 에이전시/소속, 포트폴리오 |
- 한 사람이 여러 유형을 가질 수 있게(예: 보조출연 + 이미지단역) **유형은 복수 선택**.
- 필요 인원 등록 때 "유형 + 요건(성별·나이·키·언어 등)"을 걸고, 요건에 맞는 이용자에게만 신청 버튼이 열린다(기존 `Eligibility` 확장).
- 외국인은 **식별번호가 외국인등록번호**이므로 지금의 주민번호 구조(암호화·마스킹·감사)를 "식별번호 종류"로 일반화한다.

### 4-4. 일정 = 공고 (단순화)
```
작품(촬영 건) ─ 촬영일정(날짜·시간·장소) ─ 필요 인원(유형·요건·정원·보수 안내)
                                           └─ 공개 상태: 비공개(초안) / 공개 / 마감
```
- "공고 게시" 버튼 없이 **일정을 저장하면 공개 상태에 따라 바로 보임**(초안 상태로 두면 안 보임 — 실수 방지용으로 권장).
- 수정은 즉시 반영하되, **이미 신청자가 있는 일정의 날짜·시간·장소를 바꾸면** 신청자에게 알림(기존 연기 기능 재사용).
- 사유 칸: 이용자의 **신청 사유**(선택)·**취소 사유**(필수 권장), 팀장의 **등록·취소 사유**.

### 4-5. 팀장 등록
- 일정마다 `schedule_team_leaders(일정, 직원, 상태, 사유, 등록자)` 한 줄. 팀장이 스스로 등록하면 상태는 즉시 `등록됨`(사용자 설명 기준), 실장 이상이 대신 등록·해제 가능. 취소 시 사유 기록.
- 일정 화면에 "팀장 N명 필요 / 등록 M명"을 표시(필요 팀장 수는 일정에 입력).

## 5. 외부 사실·법적 주의 (◐ 미확인, 공식 확인 필요)
- 외국인이 **수익을 목적으로 방송에 출연**하면 체류자격(E-6 예술흥행 등) 문제가 생길 수 있다. 자료들은 방송 출연이 E-6-1 에 속하고, **90일 이내 단기는 C-4**, 그 이상은 E-6 로 안내한다. 단역이라고 예외라는 근거는 찾지 못했다. 근거: [E-6 안내](https://kowork.kr/visa/E-6), [E-6 가이드(2025)](https://visainfo-korea.com/entry/2025-%EC%B5%9C%EC%8B%A0-E-6-%EB%B9%84%EC%9E%90%EC%98%88%EC%88%A0%ED%9D%A5%ED%96%89-%EC%99%84%EB%B2%BD-%EA%B0%80%EC%9D%B4%EB%93%9C).
  → **서비스는 "체류자격을 입력·서류 확인하는 기능"까지만** 만들고, 합법 여부 판단은 OIO 가 출입국(1345) 등에 확인. 코드는 "확인 완료 표시·확인자·확인일"만 남긴다.
- 사용자가 앞서 "법무 확인은 생략"으로 결정한 것은 **근로계약서·임금 지급이 없다는 전제**였다. 외국인 출연 서류·체류자격과 식별번호 수집은 다른 문제라서, 오픈 전 OIO 내부 또는 출입국 확인을 권한다(결정은 사용자 몫).

## 6. 구현 단계 (제안)
| 단계 | 내용 | 기존 코드 영향 |
|---|---|---|
| A. 기반 | OIO 시드, 직원 초대·생성, 직급 확장, 권한 표(DB), 첫 화면 분기 | 업체 등록 화면 숨김, 직책 검사를 권한 검사로 교체 |
| B. 일정 = 공고 | 작품·일정·필요 인원 화면, 공개 상태, 수정 알림 | `PostingService` 재구성(공고와 일정 합침) |
| C. 이용자 유형 | 유형 복수 선택, 유형별 프로필, 요건 확장 | `Eligibility`·프로필 확장 |
| D. 팀장 | 팀장 등록/배정/취소·사유 | 새 테이블·화면 |
| E. 외국인 | 식별번호 종류, 체류자격 확인 표시, 영어 화면 | 주민번호 모듈 일반화, 앱 i18n |
| F. 총괄 메뉴 | 계정·권한·삭제·복구·감사 | 관리자 화면 확장 |
각 단계는 지금처럼 **스키마·시험·화면·문서를 함께** 끝내고 푸시한다. A~B 가 끝나면 OIO 직원이 바로 써 볼 수 있다.

## 7. 사용자가 정해 주세요 (제 추천을 먼저 적음)
1. **직급 목록과 서열**이 맞나요? (대표·이사·실장·팀장·직원 + 스케줄러 기능, 더 있으면 알려 주세요) — 추천: 위 표 그대로.
2. **이사도 일정 등록 가능**한가요? **실장**은 선발(합격 통보)까지 가능한가요? — 추천: 이사 ✔, 실장은 열람+팀장 배정만.
3. **팀장 스스로 등록은 즉시 확정**인가요, 아니면 실장 이상 승인이 필요한가요? — 추천: 즉시 확정 + 실장 이상이 해제 가능.
4. **선발은 누가** 하나요? 스케줄러만? 팀장 추천 후 승인? — 추천: 스케줄러·이사·대표가 선발, 팀장은 추천 표시만.
5. **이용자 유형은 복수 선택**을 허용할까요? — 추천: 허용.
6. **이미지단역·단역은 오디션형**(사진/영상 보고 선택, 신청 후 대기)인가요, 보조출연처럼 선착순에 가까운가요? — 기존 정책은 "업체가 보고 뽑음"이라 이미 오디션형. 유지 추천.
7. **외국인 이용자 화면은 영어도 필요**한가요? — 추천: 영어 지원(앱 우선).
8. **다른 업체가 가입하는 구조는 완전히 접나요**, 숨기기만 할까요? — 추천: 숨기기만(삭제 없이).
9. **신청 사유는 필수**인가요? **취소 사유**는요? — 추천: 신청 사유 선택, 취소 사유 필수.
10. 기존 정책 중 바뀌는 것이 있나요? (예: 수수료 0원·무료, 주민번호는 첫 지원 전, 구독은 업체만) — 구독은 OIO 1곳이면 의미가 없어져 보류 추천.
