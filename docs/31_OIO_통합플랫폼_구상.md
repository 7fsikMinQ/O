# 31. OIO 캐스팅 통합 플랫폼 구상 — 이용자 + 직원(사내) 한 플랫폼 (v2, 2026-11-16, 사용자 1차 답변 반영)

> 사용자가 "OIO(단역·이미지단역·보조출연 캐스팅 회사)에 소속되어 이용자용 + 직원용을 합친 플랫폼"으로 방향을 넓혔다. 이 문서는 사이클 정리, 유사 서비스 비교, 구상, 기존 구현과의 차이, 단계 계획, 남은 질문을 담는다.
> **확정(사용자 2026-11-16)** 과 **제안(Claude)** 을 구분해 적었다. 확정분만 CLAUDE.md §10 에 옮겨 두었고, 제안은 사용자 확인 전까지 코드에 반영하지 않는다. 외부 사실은 블로그·앱스토어 소개 등 2차 자료라 ◐(미확인)이다.

## 0. 사용자 확정 사항 (2026-11-16)
1. **외국인(외국인단역·외국인출연자)은 제외, 국내만.** 이용자 유형은 보조출연·단역·이미지단역 3종.
2. **선발은 스케줄러·이사·대표.** 팀장 등록은 **등록하면 바로 확정**, 이후 **수정 가능**, **삭제는 윗 직급**이 한다. (해석은 §1-3 에서 확인 요청)
3. **직원 직급**: 대표, 이사, 현장 실장, 현장 팀장, 스케줄러, 캐스팅 매니저 등(목록은 추가 가능해야 함). **총괄(개발자)은 전부 수정·삭제 가능.**
4. **신청 사유·취소 사유**: 선택지는 Claude 가 추천하고, **기타는 직접 작성**.
5. **웹앱(PWA) + 구글 플레이 + 애플 앱스토어까지.**
6. **초기 개발은 직원용부터. 이용자용은 숨겨 두고, 개발이 끝나면 공개.**

## 1. 전체 사이클 (재정리)

### 1-1. 사용자 세 종류
| 구분 | 누구 | 하는 일 |
|---|---|---|
| **이용자** (공개 영역) | 보조출연·단역·이미지단역 출연자 | 가입 → 프로필 등록(사진 등) → 공고 조회 → 신청(사유) → 합격 통보 → 확정, 취소(사유) |
| **직원** (OIO 소속) | 대표·이사·현장 실장·현장 팀장·스케줄러·캐스팅 매니저·직원 | 촬영 일정·필요 인원 관리, 선발, 팀장 등록, 현장 운영. 직급별 권한 다름 |
| **총괄** (개발자) | 개발 담당 | 모든 수정·삭제, 직원·직급·권한·설정, 복구, 감사 로그 |

### 1-2. 한 사이클 (촬영 한 건)
1. **일정 등록** — 대표·이사·스케줄러가 촬영(작품·날짜·장소·시간)을 등록·수정. 저장하면 공개 상태에 따라 이용자 화면에 **바로 반영**.
2. **필요 인원 등록** — 날짜별로 유형·요건·인원(정원)을 적음.
3. **이용자 신청** — 이용자가 공고를 보고 신청(사유 선택/기타).
4. **선발·확정** — 스케줄러·이사·대표가 선발 → 이용자 확정(기존 2단계 확정 유지).
5. **팀장 등록** — 현장 팀장이 일정을 보고 등록(즉시 확정), 실장·이사·대표·스케줄러도 대신 등록 가능. 수정 가능, 삭제는 윗 직급. 등록·취소에 사유.
6. **취소** — 이용자 취소·팀장 취소 모두 사유(선택지+기타).
7. 현장 출석·인원표·메시지는 기존 기능 재사용.

### 1-3. 해석을 확인하고 싶은 부분
- "팀장 등록하면 확정되지만 수정되고 윗 계급이 삭제 가능": **팀장 등록은 승인 절차 없이 즉시 확정**, 등록 후 내용(담당 일정·메모)은 수정 가능, **삭제(해제)는 등록한 사람보다 윗 직급**이 한다고 읽었습니다.
- 캐스팅 매니저는 **출연자 프로필·신청 열람, 연락(메시지), 선발 추천**을 하고 일정은 수정하지 않는다고 가정했습니다.

## 2. "다른 업체 가입 구조"란? (용어 설명)
지금 만들어 둔 시스템은 **여러 회사가 쓰는 장터형**입니다. 누구나 가입 → "업체 등록"(상호·사업자번호) → 관리자 승인 → 그 회사가 공고를 올립니다. OIO 한 회사만 쓴다면 이 "업체 등록·승인" 화면이 필요 없습니다. OIO 는 미리 등록해 두고 직원은 **대표·총괄이 계정을 만들어 주는** 방식이 됩니다. 제안: **화면만 숨기고 코드는 지우지 않기**(나중에 협력 업체를 받고 싶어질 수 있어서).

## 4. 구상

### 4-1. 화면 구조와 "웹앱 + 스토어"
```
          ┌────────────── 서버·DB (하나) ──────────────┐
 직원 웹(PC, React, 설치형 PWA)        출연자·현장 앱(Flutter 한 코드)
  일정표·필요 인원·선발·팀장·표·엑셀      Android(플레이스토어) · iOS(앱스토어) · 웹/PWA
  총괄 메뉴(계정·권한·삭제/복구·감사)      첫 화면: [이용자로 시작] / [직원 로그인]
```
- **직원 PC 업무**(일정표·표·엑셀·권한 관리)는 화면이 넓은 **React 웹**이 낫다. 지금 있는 업체 웹을 직원용으로 개편한다.
- **현장 업무**(오늘 일정, 팀장 등록, QR 스캔, 인원 체크, 전화·메시지)는 휴대폰이 필요하다. 제안: **Flutter 앱에 "직원 모드"** 를 추가해 한 앱(스토어 등록 1건)으로 이용자·직원이 로그인 유형에 따라 갈라지게 한다. 현장용 최소 기능만 만들어 두 벌 유지 비용을 줄인다.
- 웹 래퍼(웹뷰)만 씌운 앱은 애플 심사에서 거절될 위험이 있다(◐ 일반적 심사 지침, 제출 전 최신 지침 확인). 그래서 직원 모바일은 웹뷰 대신 Flutter 로 만드는 쪽을 권한다.

### 4-2. "이용자용 숨김"을 어떻게 하나
- `feature_flags` 에 **`ACTOR_AREA`**(이용자 영역 공개)를 추가한다. **개발 PC=켬(지금 시험이 그대로 돈다), 운영=끔.**
- 끔일 때: 이용자 가입·로그인·공고 조회 API 는 막고(서버 404), 앱·웹 첫 화면에서 "이용자로 시작"을 숨긴다. 직원 영역은 정상.
- 공개 시점에 스위치만 켠다. 코드를 다시 만들 필요가 없다.
- **스토어 제출 주의(◐)**: 심사에서는 이용자 기능이 실제로 보여야 하고 심사용 데모 계정이 필요하다(정책 19의 `REVIEW_DEMO_LOGIN`). 숨긴 기능이 있는 채로 제출하면 거절될 수 있으므로 **스토어 제출은 이용자 영역을 켠 뒤**에 한다. 그 전까지 직원은 웹/PWA 와 내부 테스트 배포로 쓴다.

- 유형은 **복수 선택**, 필요 인원 등록 시 유형·요건을 걸고 요건이 맞는 이용자에게만 신청이 열린다(기존 `Eligibility` 확장).

### 4-5. 일정 = 공고 (이미 대부분 있음)
현재 구조가 이미 `공고(작품) → 일정 → 역할(필요 인원)` 이고 DRAFT/OPEN/CLOSED/CANCELED, 수정·복사·마감·재오픈이 있다. 새로 필요한 것은 ① 직원 화면을 "일정 등록 = 공고" 흐름으로 정리 ② 신청자가 있는 일정의 날짜·시간·장소를 바꿀 때 신청자 알림 ③ 초안(비공개) 표시. **공고 재구성이 아니라 화면·알림 보강**이라 생각보다 작다.

### 4-6. 사유 (선택지 추천 + 기타 직접 작성)
저장은 `reason_code`(선택지) + `reason_text`(기타일 때 필수, 200자 이내)로 통일한다.
| 상황 | 필수 여부 | 추천 선택지 |
|---|---|---|
| 이용자 **신청** 사유 | 선택 | 해당 역할 경험 있어요 / 의상·분장 준비 가능 / 특기가 있어요(운전·악기 등) / 처음이지만 열심히 할게요 / 기타 |
| 이용자 **취소** 사유 | **필수** | 몸이 아파요 / 가족 사정(경조사) / 다른 촬영과 겹쳐요 / 교통·거리 문제 / 개인 사정 / 기타 |
| 팀장 **등록** 사유 | 선택 | 담당 현장 경험 / 인원 부족 보충 / 요청받음 / 기타 |
| 팀장 **취소·삭제** 사유 | **필수** | 다른 현장 일정 / 건강 / 개인 사정 / 인원 조정 / 입력 실수 / 기타 |
| 직원 **일정 변경·삭제** 사유 | **필수** | 촬영 일정 변경 / 인원 조정 / 촬영 취소 / 입력 실수 / 기타 |
이용자 취소 사유는 기존 "확정 후 취소 판정(스케줄러 투표)"의 판단 자료로 계속 쓰인다.

## 6. 기존 구현과의 차이 (외국인 제외 반영)
| 항목 | 지금 | OIO 방향 | 영향 |
|---|---|---|---|
| 업체 | 누구나 가입→승인 | OIO 1곳, 직원은 초대·생성 | 업체 등록 화면 숨김(코드 유지), OIO 시드 |
| 직책 | 5종 코드 고정 | 직급 목록+권한 항목(DB) | `Roles.java`·약 52곳·`member_role` CHECK 변경 (V1 은 첫 운영 배포 전이라 재생성 가능) |
| 유형 | 1종 | 보조출연·단역·이미지단역 복수 | 프로필·요건 확장 |
| 팀장 | 직책만 | 일정별 팀장 등록·수정·삭제 | 새 테이블 `schedule_team_leaders` |
| 사유 | 취소 사유 | 신청·취소·팀장·직원 변경 | `reason_code`+`reason_text` |
| 이용자 영역 | 항상 공개 | `ACTOR_AREA` 로 숨김/공개 | 기능 플래그·화면 숨김 |

## 7. 구현 단계 (제안, 직원용 먼저)
| 단계 | 내용 |
|---|---|
| A. 기반 | OIO 시드, 직원 초대·생성, 직급 목록+권한 항목(DB), `ACTOR_AREA` 스위치, 업체 등록 화면 숨김, 첫 화면(직원 로그인 중심) |
| B. 일정=공고 | 직원 화면 개편(일정·필요 인원·공개 상태), 변경 알림, 사유 선택지 공통 컴포넌트 |
| C. 팀장 | 팀장 등록·수정·삭제와 사유, "팀장 N명 필요/M명 등록" |
| D. 직원 모바일 | Flutter 직원 모드: 오늘 일정, 팀장 등록, QR 스캔, 인원 체크 |
| E. 이용자 유형 | 유형 복수 선택, 유형별 프로필·요건, 이미지단역 사진 다수 |
