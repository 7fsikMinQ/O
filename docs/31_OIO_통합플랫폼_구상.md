# 31. OIO 캐스팅 플랫폼 최종 설계 (v4, 2026-11-19) — 바로 작업할 수 있는 기준 문서

> OIO(법인, 단역·이미지단역·보조출연 캐스팅)의 플랫폼. **4단계**로 키운다: ① 직원 전용 사이트 → ② 앱(직원 모바일, 스토어) → ③ 외부 배우·출연자 가입 + **오디션 영상·이력서 DB**(동의서 수집) → ④ 수집한 자료의 **상업적 제공·판매**(AI·숏폼·이미지/얼굴 용도 포함).
> 이 문서가 **전체 설계의 기준**이다. 세부는 [32 권한·API 보안](./32_권한_API_보안_설계.md), [33 UI 디자인 시스템 v2](./33_UI_디자인_시스템_v2.md). **확정**=사용자가 정함, **제안**=Claude 권고(사용자 확인 후 반영). 외부 사실은 2차 자료라 ◐(미확인).
> v3 의 "UNCLAIMED(직원이 대신 등록하는 미가입 출연자)"는 **폐기**한다(§0-6). v2·v3 의 스토어·접근 제한 관련 내용 중 이 문서와 다른 것은 이 문서가 우선한다.

## 0. 확정 사항 (사용자, 2026-11-16~19)
1. **소속·유형**: OIO 법인. 보조출연·단역·이미지단역(국내만, 외국인 제외).
2. **단계적 확장**: 직원 전용 사이트 → 앱 → 외부 출연자 가입·DB → 상업적 제공.
3. **직급**: 대표, 이사, 현장 실장, 현장 팀장, 스케줄러, 캐스팅 매니저 등. **서열·직급·권한은 나중에 관리자가 화면에서 직접 등록·추가·수정**(그 화면을 만든다). **지금은 관리자가 모든 것이 되고, 관리자 계정으로 시험한다.** 총괄(개발자)=전권.
4. **선발**은 스케줄러·이사·대표. **팀장 등록은 즉시 확정, 수정 가능, 삭제는 윗 직급**. **삭제는 무조건 관리자·윗 직급만**(일반 직원은 취소·숨김).
5. **신청·취소 사유**는 선택지(Claude 추천)+기타 직접 작성.
6. **출연자 명단 없음, 전원 신규 가입**: 동의서·개인정보 동의를 직접 받아야 하므로 **기존 명단 가져오기·직원 대리 등록 없음**.
7. **판매의 뜻**: 출연자·배우의 **오디션 자료 영상**을 받아 두고, **가입 때 동의서를 받아서** 추후 **상업적으로 판매**(AI 학습, 숏폼, 이미지·얼굴 이용 등).
8. **접속 제한 없음**: 직원은 **가입 신청 → 승인 → 권한 부여**로만 접근하고, **권한별로 기능이 열린다.** API 주소를 알아도 권한 없이는 조회·수정 불가(필터·인터셉터·AOP 로 **API 별 권한**).
9. **웹앱(PWA) + 플레이스토어 + 앱스토어**(OIO 법인 명의). 출연자 영역은 개발해 두고 **숨겨 두었다가** 준비되면 공개.
10. **UI**: 토스·당근처럼 깔끔·가시성, **AI 느낌 최소**, 폰트·색상·크기 정리, **무료·저작권 문제 없는 것만**(33번).
11. **팀장 해석(v3 질문 6)**: 확인됨(즉시 확정, 삭제는 윗 직급). **캐스팅 매니저 권한**은 답이 없어 가정(인재 DB 관리·선발 추천, 일정 수정 없음) — 직급·권한 화면에서 바꾸면 되므로 막지 않는다.

## 1. 한눈에 — 4단계
| 단계 | 누가 쓰나 | 핵심 | 대략 규모(확정 아님) |
|---|---|---|---|
| **1 직원 사이트** | OIO 직원(가입 신청→승인) | 촬영 일정·필요 인원·**팀장 등록**, 직원 승인·**직급/권한 관리 화면**, 감사·삭제/복구, 새 UI | 7~10주 (구조 분리 포함) |
| **2 앱** | 직원(현장) | Flutter 직원 모드(오늘 일정·팀장 등록·QR), 스토어 등록 | 4~6주 |
| **3 출연자 + 인재 DB** | 외부 배우·출연자 + 직원 | 가입(**동의서 단계 분리**), 프로필, **이력서·오디션 영상**, 신청·확정·취소 | 6~8주 |
| **4 자료 제공(판매)** | 구매자(제작·AI 사업자 등) | 동의한 자료만 묶어 제공, 반출 기록, 철회 반영 | 6주+ |
- **1단계에는 출연자가 없다**(전원 신규 가입이 원칙이므로 3단계부터). 그래서 1단계는 일정·필요 인원(숫자)·팀장·직원 관리까지가 범위다. 이미 만든 출연자 앱·API·시험은 **그대로 두고 `ACTOR_AREA` 스위치로 숨긴다**(개발 PC 켬, 운영 끔).
- 다음 단계는 앞 단계가 안정된 뒤 시작한다(1단계만 운영해도 직원 업무에 가치가 있도록).

## 3. 동의서·자료 상업 이용 설계 (가장 중요하고 가장 위험한 부분)
> 영상·사진에는 **얼굴·목소리**가 들어 있다. 이를 AI 학습·합성(얼굴/음성)·숏폼·이미지 용도로 **판매**하려면 **초상·성명·음성 이용 허락, 개인정보 제3자 제공·목적 외 이용 동의, 저작·실연 권리 정리**가 모두 필요하다(◐ 일반 원칙, 구체 조항은 확인 필요). 이 설계는 "나중에 문제 없이 팔 수 있는 자료만 쌓는" 데 초점을 둔다.

### 3-1. 법적·구조 원칙 (제안, ◐ 변호사 확인 필수 — 3단계 가입 화면을 열기 **전**)
1. **목적별로 분리해서 동의**를 받는다(한 장에 뭉뚱그려 받지 않는다).
2. **필수가 아닌 동의(AI·판매·합성)는 거부해도 가입·지원·출연이 된다**(서비스 제공의 조건으로 삼지 않는다 — 선택 동의 거부를 이유로 한 서비스 거부 금지 원칙, ◐ 확인). 그래서 **판매 가능한 자료의 양은 출연자의 동의율에 달려 있다** → 동의 화면을 쉽고 설득력 있게 만든다(§3-3).
3. **얼굴·음성 합성**처럼 영향이 큰 이용은 **별도 항목·구체 설명·기간·범위·대가**를 적는다(포괄 동의 ✕).
4. **철회 가능**하고, 철회 후에는 **새 제공·반출에서 제외**한다. 이미 제공한 자료의 처리는 **구매 계약에 미리 명시**(삭제 요청 전달·재사용 금지 등).
5. 만 19세 미만은 가입 불가(기존 정책)이므로 미성년 동의 문제는 제외.
6. **가명처리·최소 제공**: AI 학습용 제공본은 이름·연락처·주민번호 등 식별 정보를 제거하고 내부 비식별 ID 로만 제공(◐ AI 학습 개인정보 특례·가명처리 기준은 2026년 개정이 있었다는 보도가 있어 시행 시점·세부를 확인).
7. 개인정보 영향 평가·처리방침 개정·위탁/제공 현황 고지(변호사·개인정보 담당 확인).

### 3-2. 동의 항목(제안)
| 코드 | 이름 | 필수 | 내용 요지 |
|---|---|---|---|
| `SERVICE` | 서비스 이용약관 | 필수 | 계정·이용 규칙 |
| `PRIVACY` | 개인정보 수집·이용 | 필수 | 가입·캐스팅 업무에 필요한 항목 |
| `PORTFOLIO_STORE` | 영상·이력서·사진 보관 | 필수(영상 제출 시) | OIO 가 오디션 자료를 보관·열람(직원 권한 범위) |
| `CASTING_USE` | OIO 내부 캐스팅 활용 | 필수(제출 시) | 캐스팅 후보 검토·제작사 제안 시 **OIO 가 중개** |
| `THIRD_PARTY` | 제3자 제공 | **선택** | 제작사·에이전시 등에 자료 열람·제공 |
| `AI_TRAINING` | AI 학습 이용 | **선택** | 비식별 처리한 영상·이미지를 AI 모델 학습에 사용·제공 |
| `LIKENESS_SYNTH` | 얼굴·음성 합성·재현 이용 | **선택** | 영상·사진 속 얼굴·음성을 합성·재현물 제작에 이용 |
| `SHORTFORM_IMAGE` | 숏폼·이미지 콘텐츠 이용 | **선택** | 편집된 숏폼·이미지 콘텐츠에 이용 |
| `MARKETING` | 소식 받기 | 선택 | 알림 |
각 항목에 **버전·적용 범위(어디까지)·이용 기간·대가(있다면)·철회 방법·철회 효과**를 문서로 둔다(`terms` 확장). 동의·철회는 **시각·버전·IP/기기·화면 캡처 해시**를 증빙으로 저장(기존 서명·증빙 구조 재사용).

### 3-3. 가입 화면 흐름 (동의율을 높이면서도 적법하게)
1. 이메일 인증 → 이름 → **필수 동의 3개**(한 화면, 각각 펼쳐 보기).
2. **"자료 활용 동의" 별도 화면**: 항목마다 한 줄 설명 + 자세히 + 스위치. **기본값 꺼짐**(미리 체크 ✕). "나중에 설정에서 바꿀 수 있어요" 안내.
3. 영상·이력서 올리기 화면에서 **그 자료에 적용될 동의 상태를 표시**("이 영상은 내부 캐스팅에만 사용돼요 / AI 학습에 사용 가능해요").
4. 설정 > 동의 관리: 항목별 켜기·끄기, 철회 시 영향 안내, 이력 보기.
- 동의를 받기 위한 **혜택(예: 우선 안내 등)은 가능하되 불이익 금지**(◐ 확인). 대가 지급 여부·수익 배분은 **OIO 사업 결정 사항**이며 정해지면 동의서에 명시한다.

### 3-4. 자료·반출 파이프라인 (4단계 대비, 3단계 데이터 모델에 미리 반영)
| 요소 | 설계 |
|---|---|
| 자료 | `talent_media`(영상·이력서·사진: 소유자·종류·파일·길이·촬영 일자·**제출 시 적용된 동의 스냅샷**) |
| 동의 | `user_consents`(코드·버전·동의/철회 시각·증빙) — 항목별로 **현재 유효 여부**를 조회하는 뷰 `v_active_consents` |
| 반출 후보 | "해당 코드에 현재 유효 동의가 있는 자료"만 조건 질의로 추림(**동의 없는 자료는 구조적으로 선택 불가**) |
| 반출 | `dataset_exports`(구매자·목적·동의 코드·기간·자료 목록 해시·반출자·시각), 반출본은 **비식별 ID+워터마크/해시**, 파일은 만료되는 서명 링크 |
| 철회 | 동의 철회 시 그 사람의 자료는 **이후 반출 후보에서 제외**, 진행 중 반출은 알림, 이미 제공본은 계약 조항으로 처리 |
| 열람 로그 | 직원·구매자의 영상 열람은 모두 기록하고 출연자가 "누가 봤는지" 확인(요약) |
| 접근 | `TALENT_MEDIA_READ` 권한자만 영상 재생(서명 URL 5분), 다운로드는 별도 권한 |
- **영상 저장·비용(◐ Cloudflare 공식 문서 인용 블로그)**: R2 저장 약 US$0.015/GB·월(내려받기 무료), Stream 은 저장 US$5/1,000분·재생 US$1/1,000분. **처음엔 R2 + 서명 URL 재생**(mp4/H.264, 1건 3분·200MB·3개 제한)으로 비용 상한을 두고, 필요하면 Stream 으로 이전. 대용량 업로드는 브라우저→R2 직접 업로드(서명 URL)로 새로 만든다.

## 10. 구조 결정 — 직원 플랫폼과 출연자 플랫폼 분리 (제안, 2026-11-20)
> 사용자 제안: "직원용과 출연자용은 서로 다른 플랫폼으로 하고 DB만 공유하는 형식". **방향에는 동의**하되, 두 플랫폼이 같은 업무 규칙(합격 통보·확정, 인원 초과 방지, 동의 판단)을 따로 구현하면 어긋날 위험이 크므로 **"코드는 하나(공유 핵심), 실행 프로그램은 둘, DB는 하나(계정 분리)"** 방식을 권한다. 사용자 확정 전까지 코드는 바꾸지 않는다.

### 10-1. 선택지 비교
| 구분 | A 현재(서버 1개, 스위치로 숨김) | B 완전 분리 + DB 직접 공유(제안 그대로) | **B′ 권장: 공유 핵심 + 실행 2개 + 계정 분리 DB** | C 완전 분리 + DB 도 분리 |
|---|---|---|---|---|
| 보안 격리 | 약함(공개·직원 기능이 한 프로그램) | 강함 | **강함** | 가장 강함 |
| 업무 규칙 중복·불일치 위험 | 없음 | **높음**(같은 표를 두 곳에서 수정) | 낮음(규칙은 공유 핵심 한 곳) | 중간(연동 규칙 필요) |
| 1인 개발 부담 | 가장 작음 | 큼(두 벌) | 중간(+1~2주, 추정) | 매우 큼 |
| 운영·서버 | 1개 | 2개 + DB | 1단계는 1개, 3단계에 2개 | 2개 + DB 2개 |
| 출연자 영역 숨김 | 스위치(코드는 배포됨) | 배포 자체를 안 함 | **배포 자체를 안 함** | 배포 자체를 안 함 |
| 스키마 변경 | 쉬움 | **양쪽 동시 수정** | 한 곳(핵심)에서만 | API 계약 변경 |
**권장 B′.** 이유: ① 1~2단계에는 출연자용 프로그램을 아예 배포하지 않아 "숨김"이 아니라 "없음"이 된다. ② 공개 인터넷에 노출되는 출연자용이 뚫려도 직원용 기능·권한·감사 데이터에 닿지 못한다. ③ 합격·확정·동의 같은 핵심 규칙은 한 곳에 있어 어긋나지 않는다.

### 10-2. B′ 설계 요점
| 항목 | 내용 |
|---|---|
| 코드 구성 | 저장소 하나, 모듈 4개: `core`(도메인 규칙·DB 접근·마이그레이션 소유), `staff-api`(직원 기능·직원 인증), `actor-api`(출연자 기능·공개 공고·출연자 인증), `worker`(메일·알림 발송, 기존 아웃박스) |
| DB | PostgreSQL 하나. **마이그레이션은 `core` 한 곳에서만** 실행. DB 계정 3개: `app_owner`(마이그레이션 전용), `staff_app`, `actor_app` |
| DB 권한 분리 | `actor_app` 은 출연자 영역 테이블·열만 GRANT(직급·권한·감사·구매자·반출 테이블 접근 불가). 직원 전용 데이터는 출연자용 프로그램이 읽을 수 없음 |
| 토큰 분리 | 직원 토큰과 출연자 토큰의 **발급자·서명 키·대상(audience)을 다르게** 한다. 출연자 토큰으로 직원 API 를 부르면 기본 차단 |
| 주소 | 직원용 `staff.도메인`, 출연자용 `app.도메인`. CORS·속도 제한·방화벽 규칙을 각각 설정 |
| 민감정보 | 선택 강화(3단계): 출연자용 프로그램은 주민번호·계좌를 **쓰기 전용**(공개 키로 암호화)으로 받고, **복호화 키는 직원용에만** 둔다 |
| 알림 연결 | 직원 쪽 변경(일정 수정 등)은 DB 의 아웃박스 테이블로 전달하고 worker 가 출연자에게 알림(이미 구현된 방식) |
| 배포 | **1~2단계: `staff-api`(+DB)만 배포.** 3단계에 `actor-api` 추가. 3단계에는 서버 사양 상향이 필요할 수 있음(JVM 2개+DB, 가격은 확인) |

### 10-3. 주의(공유 DB 의 단점을 줄이는 규칙)
1. **스키마 소유자는 `core` 하나.** 두 프로그램이 각자 테이블을 바꾸지 않는다.
2. 스키마 변경은 **확장 → 양쪽 전환 → 정리** 순서(한 번에 깨뜨리지 않기).
3. CI 에서 `staff-api`·`actor-api` 시험을 **같은 DB 로 함께** 돌린다.
4. 공개 공고 같은 출연자용 조회는 직원 쪽 원본 테이블이 아니라 **조회용 뷰**로 노출한다.
5. 직원·출연자 계정은 `users` 한 곳에 두되 로그인 경로와 토큰은 분리한다(한 사람이 직원이면서 출연자일 수 있음).

### 10-4. 일정·비용 영향(추정)
- 1단계 +1~2주(모듈 분리, DB 계정·토큰 분리, 시험 이전). 1단계 **7~10주**, 전체 **약 24~32주 이상**.
- 운영비: 1~2단계는 변화 없음(프로그램 1개). 3단계부터 서버 사양 상향 가능성.
