# 02. 프로세스 정의서

> v1.0 · 2026-10-28 · 요구사항(01)·기능(03)과 ID 로 연결. 다이어그램은 Mermaid.
> 용어: 업체=보출 업체, 출연자, 반장=`FIELD_LEADER`, 시스템=서버/배치.

## 목차
1. 가입·업체 승인 / 2. 공고 등록·게시 / 3. 탐색·지원 / 4. 선발·합격 통보 / 5. 마감 자동 불합격 / 6. 합격 이후(단체 메시지·인원표·정보표) / 7. 전날 참석 확인 → 당일 출석 / 8. 일자 취소·연기 / 9. 정산 기록 / 10. 미성년자 동의서 / 11. 알림 파이프라인 / 12. 탈퇴·파기 / 13. 구독 게이트 판정

## 1. 가입 · 업체 승인 (REQ-A01~A07, C01, M01)
```mermaid
flowchart TD
  A["앱/웹 진입"] --> B{가입 유형}
  B -->|출연자| C["이메일/소셜 가입 + 약관 동의 + 휴대폰 인증"]
  B -->|업체| D["이메일/소셜 가입 + 약관 동의"]
  C --> E[프로필 작성: 신체·사진·기본 정산정보]
  E --> F{만 19세 미만?}
  F -->|예| G["법정대리인 동의서 제출 → 운영자 검수"]
  F -->|아니오| H[지원 가능]
  G -->|승인| H
  D --> I[업체 등록: 사업자번호·대표자·등록증 업로드]
  I --> J["(companies=PENDING)"]
  J --> K[관리자 서류 검토]
  K -->|승인| L["APPROVED → 공고 게시 가능 + 알림"]
  K -->|반려| M["사유 안내 → 재제출"]
```
| 단계 | 담당 | 입력 → 출력 | 예외/규칙 |
|---|---|---|---|
| 가입 | 사용자 | 이메일·비밀번호·약관 → `users`, `user_roles`, `user_consents` | 중복 이메일/휴대폰 409, 필수 약관 미동의 422 |
| 휴대폰 인증 | 출연자 | 번호·코드 → `phone_verified_at` | 번호 유일, 5회 실패 시 제한 |
| 업체 등록 | 업체 | 사업자 정보+파일 → `companies`(PENDING), `company_members`(OWNER), `company_verifications` | 사업자번호 유일 |
| 승인 | 관리자 | 승인/반려+사유 → 상태 변경, `audit_logs`, `COMPANY_APPROVED` 이벤트 | **미승인 업체는 공고 게시 불가(403 `COMPANY_NOT_APPROVED`)** |

## 2. 공고 등록 · 게시 (REQ-J01~J10)
```mermaid
flowchart TD
  A[업체 직원: 공고 작성 시작] --> B["작품 선택/신규 입력"]
  B --> C[일자 추가 N: 날짜·집합시간·장소·철야·담당 반장]
  C --> D[일자별 역할 추가 N: 인원·예비·성별·출생연도·키·보수·연장·식대·의상·모집방식]
  D --> E{임시저장?}
  E -->|예| F["(DRAFT)"]
  E -->|게시| G{업체 APPROVED 이고 필수값 충족?}
  G -->|아니오| H[오류 안내]
  G -->|예| I["(OPEN) + JOB_PUBLISHED 이벤트"]
  I --> J["저장검색 일치자/긴급 알림"]
```
- **복사**: 이전 공고의 일자·역할 구조를 날짜만 옮겨 새 DRAFT 로 만든다. 지원자·확정자·출결은 복사하지 않는다.
- **수정 제한**: 지원자가 있는 역할의 정원 감소/삭제는 거부(409), 보수·의상·집결 변경은 허용하되 이미 합격한 사람에게 변경 알림 발송.
- 역할의 집합 시간·장소는 비어 있으면 **일자 값을 상속**한다.

## 3. 탐색 · 지원 (REQ-S01~S05, AP01~AP05, A08)
```mermaid
sequenceDiagram
  actor U as 출연자(앱)
  participant API as 서버
  participant DB as DB
  U->>API: GET /jobs/calendar, /jobs (필터)
  API-->>U: 달력 집계/목록
  U->>API: GET /positions/{id}/apply-form
  API->>DB: 프로필·계좌·미성년/동의서·겹침 조회
  API-->>U: 자동 입력값 + 자격 판정(사유 목록) + 필요한 첨부
  U->>API: presign → (스토리지 직접 업로드) → complete
  U->>API: POST /positions/{id}/applications (Idempotency-Key)
  API->>DB: 자격 재검증 → applications INSERT(정보표 스냅샷)
  alt 선착순 역할
    API->>DB: 정원 원자 증가 + 시간범위 기록 → CONFIRMED
  else 승인제
    API->>DB: APPLIED
  end
  API->>DB: 상태이력 + outbox(APPLICATION_SUBMITTED/CONFIRMED)
  API-->>U: 201 {status}
```
- 자격 판정 순서와 사유 코드는 03번 문서 **부록 D**.
- **같은 날 복수 지원 허용**: 겹침은 경고만 하고 지원은 막지 않는다. 확정 단계에서 DB 가 겹침을 차단한다.
- 지원 시 입력한 이름·번호·출발위치·계좌는 프로필을 변경하지 않고 **그 지원에만** 저장된다(스냅샷). "기본 정보로 저장" 체크 시에만 프로필 갱신.

## 4. 선발 · 합격 통보 (REQ-SEL01~SEL07, PC01, PC02, PC12, PC13)
```mermaid
flowchart TD
  A["업체: 지원자 목록 카드/그리드"] --> B["지원자 상세: 프로필·역대 합격/출석·타 공고 지원*·충돌 배지"]
  B --> C{결정}
  C -->|합격| D["정원 원자 증가 → 시간범위 기록 → CONFIRMED"]
  C -->|예비합격| E[WAITLISTED 정원 내]
  C -->|보류| F[SHORTLISTED]
  C -->|불합격| G[REJECTED]
  D -->|EXCLUDE 위반| X[409 TIME_CONFLICT: 해당 건 실패, 나머지 계속]
  D -->|정원 초과| Y[409 FULL]
  D --> H["연락처·계좌·위치 언마스킹 + 비공개 정보 공개 + 합격 알림"]
  E --> I[예비 합격 알림]
  G --> J[불합격 알림]
```
\* 타 공고 지원 열람은 `subscription_enforcement=false` 이거나 `free_open_application_history=true` 일 때 무료, 아니면 `VIEW_ACTOR_APPLICATIONS` 기능 필요. 타 업체 공고는 제목 대신 시간대·상태만 보인다.
- 일괄 처리는 건별로 성공/실패를 가려 **207 부분 성공**으로 응답한다.
- 합격 후 취소(업체)는 사유 필수 + 출연자 알림 + 정원 감소 + 예비 승격 후보 제시.

## 5. 마감 · 자동 불합격 (REQ-SEL05)
```mermaid
flowchart LR
  A[트리거: ①업체 마감 ②지원 마감시각 ③집합시각 경과 배치] --> B[대상: APPLIED, SHORTLISTED]
  B --> C["AUTO_REJECTED + 사유·시각 + 상태이력"]
  C --> D[묶음 안내 알림: 마감되어 선발되지 않았어요]
  A --> E["WAITLISTED는 유지 → 집합시각 경과 시 EXPIRED"]
```
한 트랜잭션에서 처리하고 건수를 응답(`autoRejected: n`)과 감사로그에 남긴다. 설정 `auto_reject_on_close=false` 이면 건너뛴다(예비합격은 어떤 경우에도 자동 불합격하지 않음).

## 6. 합격 이후 — 단체 메시지 · 인원표 · 인원 정보표 (REQ-PC03~PC05, PC13)
```mermaid
sequenceDiagram
  actor C as 업체/반장
  participant API as 서버
  participant OB as outbox 워커
  actor A as 합격자들
  C->>API: POST /company/broadcasts {대상,제목,내용,채널}
  API->>API: 권한(담당 일자)·월 한도(entitlement) 확인
  API->>API: job_broadcasts 저장 + 대상 산정(CONFIRMED 또는 미응답자)
  API->>OB: outbox(BROADCAST_SENT) 기록 (같은 트랜잭션)
  API-->>C: 202 {recipientCount}
  OB->>A: 인앱 알림 생성(broadcast_id) + FCM 푸시
  A->>API: 알림 열람 → read_at
  C->>API: GET /company/broadcasts → 수신/읽음 수
```
- **인원표**: `v_schedule_headcount_summary` — 일자·역할별 정원/지원/합격/참석확인/출석/노쇼.
- **인원 정보표**: `v_schedule_confirmed_roster` — 합격자 전원의 이름·번호·위치·사이즈·계좌·출석·정산. 직책별 마스킹(03 부록 B), 열람·엑셀 다운로드는 `audit_logs`.
- 합격자끼리가 아니라 **업체↔합격자** 간에만 연락처가 공개된다(출연자는 업체/반장 번호, 업체는 출연자 번호).

## 7. 전날 참석 확인 → 당일 출석 (REQ-PC06, PC07, PC08, PC09)
```mermaid
flowchart TD
  A[매일 18:00 배치] --> B["내일 촬영 CONFIRMED 전원에 참석 확인 푸시 + departure_requested_at"]
  B --> C{출연자 응답}
  C -->|참석합니다| D[departure_confirmed_at]
  C -->|어려워요| E["사유 입력 → 합격 취소 흐름 + 업체 알림 + 예비 승격 후보"]
  C -->|무응답| F["22:00 배치: 미응답자 목록 → 담당 반장/업체 푸시"]
  F --> G["반장이 전화/문자, 필요 시 알림톡 폴백(P3)"]
  D --> H[당일: 집합 2시간 전 리마인더]
  H --> I["현장 반장 출석 체크: 출석/지각/노쇼 (또는 QR/GPS 체크인 P2)"]
  I --> J{노쇼?}
  J -->|예| K["reliability_events 차감 + apply_blocked_until + 소명 경로"]
  J -->|아니오| L["퇴근·연장 입력(P2) → 정산 기록"]
```
- 출석 기록은 **담당 반장 또는 OWNER/MANAGER 만** 가능(`NOT_ASSIGNED_FIELD_LEADER`). 같은 요청 재전송은 멱등.
- 노쇼 정정(오기록)은 감사로그와 함께 가능하며 성실도 원장에 `APPEAL_RESTORE` 로 복구한다.

## 8. 일자 취소 · 연기 (REQ-J06)
```mermaid
flowchart TD
  A["업체: 일자 상태 변경 CANCELED/POSTPONED(+새 날짜)"] --> B{영향 범위 계산}
  B --> C["CONFIRMED → 합격자 필수 알림(푸시·인앱·이메일)"]
  B --> D["APPLIED/WAITLISTED → CANCELED_BY_SYSTEM + 안내"]
  C --> E["연기: 새 일자 생성 후 기존 합격자에 '유지/취소' 선택 요청 — v1은 업체가 재공고"]
```
v1 에서는 연기 시 새 일자를 만들고 합격자가 **자동 이전되지 않는다**(업체가 단체 메시지로 안내하고 필요 시 재확정). 자동 이전은 P3 검토.

## 9. 정산 기록 (REQ-PC10) — P2
촬영 종료 → 반장/업체가 출석·퇴근 확정 → 업체가 항목(기본/연장/야간/식대/교통/보너스/공제) 입력 → `settlements`·`settlement_items` 합계 → 정산 엑셀(주민번호 제외) → 업체가 직접 이체 후 `PAID` 표시 → `sensitive_purge_days` 후 지원서 계좌 스냅샷 파기(`PGM-J07`). **플랫폼은 송금하지 않는다.**

## 10. 미성년자 동의서 (REQ-A08, AP04, M09)
```mermaid
flowchart TD
  A[출연자 생년월일 입력] --> B{만 나이}
  B -->|15 미만| X[v1 지원 불가 안내]
  B -->|15~18| C["철야·야간 일정 지원 불가 + 동의서 필수"]
  B -->|19 미만| D[동의서 필수]
  B -->|19 이상| OK[제한 없음]
  C --> E["동의서 + 가족관계 증명 업로드"]
  D --> E
  E --> F["운영자 검수: 승인/반려(사유)"]
  F -->|승인| G["valid_until 설정 → 역할 allow_minor 인 공고에 지원 가능"]
  F -->|반려| H[재제출 안내 알림]
  G --> I["유효기간 경과 시 EXPIRED(PGM-J12) → 재제출"]
```
임계값(15/18/19)은 `app_settings` 로 조정한다. 법령 해석은 13번 문서의 법무 확인 항목을 따른다.

## 11. 알림 파이프라인 (REQ-N01~N06, NFR10)
```mermaid
flowchart LR
  A[도메인 트랜잭션] -->|같은 TX| B["(outbox_events NEW)"]
  B --> C[OutboxRelay 3초]
  C --> D["알림 생성 notifications + 수신설정/광고시간 판정"]
  D --> E["(notification_deliveries PENDING)"]
  E --> F[NotificationDispatcher]
  F --> G{채널}
  G -->|PUSH| H[FCM]
  G -->|EMAIL| I[메일 API]
  G -->|KAKAO/SMS| J[P3 유료 어댑터]
  H & I & J --> K{결과}
  K -->|성공| L[SENT]
  K -->|실패| M["재시도(지수) → FAILED"]
  H -->|토큰 무효| N[device_tokens revoked]
```
인앱 알림은 항상 생성되고, 푸시/메일은 수신 설정과 필수 여부로 결정한다. 광고성은 21~08시에 보류했다가 08시에 발송한다.

## 12. 회원 탈퇴 · 파기 (REQ-A06)
탈퇴 요청 → 진행 중 확정 건(미래 일자 CONFIRMED)이 있으면 거부 → 계정 `WITHDRAWN`, 토큰·기기 폐기, 공개 프로필 비노출 → 보관기간(법정 보존 의무 확인 후 설정) 경과 시 `PGM-J09` 가 개인정보 컬럼을 비식별화/삭제(출석·정산 통계는 비식별 유지) → 파기 로그.

## 13. 구독 게이트 판정 (REQ-MON01, MON02)
```mermaid
flowchart TD
  A["유료 후보 기능 호출: 타 공고 지원목록 / 엑셀 / 단체메시지 한도"] --> B{subscription_enforcement}
  B -->|false 무료 운영| OK[허용]
  B -->|true| C{기능별 무료개방 설정?}
  C -->|예 free_open_*| OK
  C -->|아니오| D{업체 활성 구독의 plan_features 에 enabled?}
  D -->|예, 한도 내| OK
  D -->|아니오| E["403 PLAN_REQUIRED + 업그레이드 안내"]
```
판정 로직은 `EntitlementService.check(company, featureCode)` **한 곳**에만 둔다. 새 유료 기능은 `plan_features` 에 `feature_code` 행을 추가하고 호출 지점에서 check 를 호출하면 된다(스키마 변경 없음).
