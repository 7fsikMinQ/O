# 98. 사용자 제안 v1.0 vs 기존 설계(v0.2) 비교 분석과 최종 결정

> 기준일 2026-10-28. 사용자가 확정한 운영 규칙 6가지와 "v1.0 최종 통합본"(사용자 작성)을 v0.2 설계와 대조해 **더 확실한 쪽**을 채택했다. 결과물은 `db/schema.sql` v1.0 + 문서 01~15.

## 1. 결론 요약
- 사용자 제안은 **현장 운영 규칙 반영이 정확**했다: 정보표 스냅샷(이름·번호·위치·계좌), 합격 후 언마스킹, 단체 메시지 원장, 마감 자동 불합격, 인원표/정보표 뷰, 미성년자 동의서, 구독 테이블 선반영. 대부분 **수용**했다.
- 다만 **그대로 쓰면 깨지는 지점 8곳**을 보정했다 (§3). 가장 중요한 것은 ① 예비합격까지 자동 불합격시키는 SQL, ② "같은 일정 내 중복 확정만 차단"으로는 **시간 겹침 확정을 막지 못하는 점**(DB `EXCLUDE` 로 해결), ③ 미성년자 동의 상태를 프로필 한 칸으로 관리하는 점이다.

## 3. 사용자 제안을 보정한 지점 (더 확실한 쪽 선택)
| # | 사용자 제안 | 문제 | 최종 | 근거 |
|---|---|---|---|---|
| 1 | 마감 시 `WAITLISTED` 까지 `AUTO_REJECTED` | 예비합격은 업체가 **통보한 상태**이고 결원 대비 목적. 마감과 동시에 지우면 예비제도가 무의미 | `APPLIED/SHORTLISTED` 만 자동 불합격, 예비는 유지 후 집합 시각에 `EXPIRED` | 사용자 정책 6의 "합격 통보 안 하고"에 예비 통보가 포함 |
| 2 | `uq_applications_confirmed_schedule (schedule_id, actor)` 로 중복 확정 차단 | **같은 일정 내 중복만** 막음. 서로 다른 공고의 겹치는 시간 확정은 DB가 못 막고 "경고"에 의존 → 동시 요청 시 이중 확정 가능 | `confirmed_time_range` + **`EXCLUDE USING gist`** (btree_gist) | 동시성 시험 PASS: 겹치는 확정 60회 동시 시도 → 1건 |
| 3 | 미성년자: `actor_profiles.parental_consent_verified` 단일 플래그 + 보호자 정보 컬럼 | 동의서는 **유효기간·검수 이력·반려 사유·건별(PER_APPLICATION)** 이 필요. 플래그 하나로는 이력/만료 불가 | `guardian_consents` 테이블(상태·유효기간·검수자), 파일은 `file_attachments(PARENTAL_CONSENT, FAMILY_RELATION_PROOF)` | 03 부록 D, 프로세스 §10 |
| 4 | 미성년 기준 "만 18세(또는 19세)" 단일 | 법적 임계가 다름: 민법 19세(동의), 근로기준법 18세(야간 제한), 15세(취직인허가) | 설정 3개: `minor_age_limit=19`, `night_restrict_age=18`, `min_actor_age=15` | 13번 §5 (#2~3) 법무 확인 항목 |
| 5 | `subscription_plans` 에 기능별 boolean 컬럼(`can_view_actor_applications` …) | 유료 기능이 늘 때마다 컬럼 추가·마이그레이션 | `plan_features(plan_id, feature_code, enabled, limit_value)` + `usage_counters`(월 한도 집계) | "확장 시 이슈 없는 설계" 요구, 14번 §1-④ |
| 6 | 시드에 PRO 49,000원 | 가격 근거 없음 | PRO 는 비활성·0원 플레이스홀더 | 14번 §3 |
| 7 | 거의 모든 FK `ON DELETE CASCADE` | 업무 데이터(지원·출석·정산) 연쇄 삭제 위험, soft delete 원칙과 충돌 | 업무 테이블 RESTRICT, 순수 하위 상세만 CASCADE | 07번 §0 |
| 8 | 뷰가 `account_number_enc`·전화 평문을 포함하고 권한 기준 언급 없음 | 뷰를 직접 조회하면 마스킹·권한 우회 | 뷰는 **백엔드 전용**임을 스키마·문서에 명시, 마스킹은 정책 클래스 단일화, 조회/엑셀 감사 | 03 부록 B, 13번 §2 |
| 9 | 지원서에 계좌 스냅샷을 영구 보관 | 불필요한 장기 보관 | `sensitive_purged_at` + 정산 후 90일 파기 배치(J07) | 13번 §1 |
| 10 | `users.phone UNIQUE NOT NULL` 전면 적용 / `password_hash NOT NULL` | 소셜 가입·관리자 계정과 충돌 | DB 는 NULL 허용, **출연자 필수·유일은 앱 규칙+부분 유니크** | 02 §1 |
| 11 | 기술 버전 "Java 21 / Boot 3.4+ / Flutter 3.24+" | 2026-10 기준 구버전 표기 | Java 25 LTS(불가 시 21), Boot/Flutter 는 착수 시 최신 안정 확인 | 10번 §3 |

## 4. 사용자 제안에서 **그대로 채택**한 것
| 항목 | 채택 이유 |
|---|---|
| `job_broadcasts` 원장 + `notifications.broadcast_id` | 단체 메시지 이력·수신/읽음 집계에 정확히 맞음 |
| `applications` 의 이름·전화·출발위치·계좌 스냅샷 컬럼 | 공고마다 바꿔 쓰는 현장 방식, 인원정보표의 원천 |
| `AUTO_REJECTED` 상태, `departure_*`, `overtime_minutes` | 현장 흐름 반영 |
| 인원표/인원정보표 **뷰 2종** | 화면·엑셀 모두 같은 원천 |
| `job_schedules.field_leader_user_id` | 담당 반장 권한 제어의 열쇠 |
| `job_positions.allow_minor`, `end_time` | 미성년 허용·역할별 종료 시각(시간 범위 계산에 필수) |
| `actor_profiles.default_departure_location`, `confirmed_count` | 지원 자동 채움, 이력 표시 |
| 역대 합격 / 지원 목록 조회 쿼리 설계, 마감 자동 처리 쿼리 | 그대로 `API-SL03/04/05` 설계에 반영(예비 제외 수정) |
| 기술: React+Vite SPA, Flutter, R2, 한국 리전 VPS, Valkey(P2) | v0.2 와 동일 결론 |
| UI 기술 제안(shadcn/ui, TanStack Table, table_calendar, Riverpod/Dio/GoRouter) | 채택 + 디자인 시스템(15번)으로 구체화 |
