# 17. 정산·임금 지급 기능의 법적·구조 분석 (v1.3)

> 질문: "업체가 일이 끝난 뒤 3.3% 를 떼고 출연자 계좌로 임금을 보내는데, 이 전달을 이 사이트를 통해 해도 문제없는가? 문제가 있으면 개발은 해 두되 기능은 숨기고 싶다."
> **이 문서는 법률 자문이 아니다.** 웹 검색(2026-10-28, 2차 자료 포함)과 설계 판단이며, 켜기 전 노무사·세무사·변호사 확인이 필요하다. 출처·신뢰도는 [16번](./16_외부사실_확인표.md).

> **사용자 결정(2026-10-28)**: 이 서비스는 근로계약서·임금 지급을 다루지 않고 지원서 중개만 하므로 **별도 법무 확인은 생략**한다. 이 문서의 확인 항목은 참고 목록으로 남기며, 주민번호 수집·보관은 개인정보보호법 사안이므로 코드의 암호화·마스킹·감사·`require_rrn_before_apply` 스위치는 유지한다.

## 1. 결론 (한 줄)
**"사이트가 돈을 받거나 들고 있거나 대신 보내는 것"은 하지 않는다. "계산·기록·이체 파일 생성·업체의 지급 완료 기록"까지만 만든다. 그것도 법무 확인 전까지 기능 플래그로 숨긴다.** 사용자의 생각("개발은 관련되게, 기능은 숨김")이 **맞는 방향**이다.

## 2. 단계별 판단
| 단계 | 내용 | 위험 | 결정 |
|---|---|---|---|
| A. 정보 제공 | 지원서·합격서·연락처·계좌 정보를 업체가 열람 | 개인정보 처리(동의·마스킹·감사) | **개발·사용** (이미 설계) |
| B. 정산 기록 | 시급×시간, 세금 계산, 업체가 "지급했다" 기록 | 계산 오류 책임, 개인정보. 돈이 오가지 않음 | 개발, **플래그 `SETTLEMENT_RECORD` OFF** |
| C. 이체 파일 생성 | 은행 대량이체 엑셀 생성 → **업체가 자기 기업뱅킹에 직접 업로드** | 계좌 정보 처리·유출. 은행 양식 확보 전엔 불가 | 개발, **플래그 `BANK_TRANSFER_FILE` OFF** |
| D. 원천징수 자료 | 지급명세·원천세 신고용 자료 엑셀(주민번호 포함 → 암호화) | 주민번호 처리, 세무 정확성 | 개발, **플래그 `WITHHOLDING_EXPORT` OFF** |
| E. 송금 실행 | 플랫폼이 계좌에서 출금·이체하거나 업체 돈을 맡아 전달 | **전자금융업(전자지급결제대행·결제대금예치 등) 등록 문제, 자금 보관·사고 책임** | **구현하지 않음.** `PAYOUT_EXECUTION` 은 설계 메모만 |

## 3. 근거와 쟁점
1. **임금 지급 원칙 — 근로기준법 제43조**: 통화로, 직접 근로자에게, 전액, 정해진 날짜에 지급. 근로자 **본인 명의 계좌로 이체**는 일반적으로 허용(근로자 동의). → 업체가 출연자 본인 계좌로 직접 보내는 구조면 문제 없다. 플랫폼이 중간에 끼면 "직접" 원칙·책임 소재가 흐려진다. 설계: 이체 파일 생성 시 **예금주=지원자 본인 이름 일치 검사**(`payout_holder_must_match`), 불일치 경고.
2. **전자금융거래법**: 이용자의 자금을 받아 정산·전달하는 서비스는 전자지급결제대행업 등록 대상이 될 수 있다(2차 자료·블로그 수준 확인, ❓). 반대로 **정보만 중계하고 자금은 이동시키지 않으면** 대상이 아니라는 해석이 일반적이다. → E 단계를 구현하지 않는 이유.
3. **3.3%(사업소득 원천징수)와 근로자성**: 3.3% 를 뗐다는 사실만으로 근로자성이 부정되지 않는다. 출연자가 업체의 지휘·감독 아래 정해진 시간·장소에서 일하면 근로자로 볼 위험이 있고, 이 경우 4대 보험·최저임금·주휴·퇴직 문제가 **업체 책임**이다. 현장에서 근로계약서를 쓰는 점은 이 위험을 낮추지만 플랫폼이 판정하지 않는다. → `tax_type`(BUSINESS_3_3 / DAILY_WAGE / NONE)을 **업체가 세무 확인 후 선택**, 기본값을 단정하지 않는다. 일용근로소득이면 소득세 2.7%(+지방세 10%), 소액부징수(일 약 18.7만 원 이하 소득세 0)가 있다(◐).
4. **신고 일정**(◐ 2차 자료, 착수 시 국세청 확인): 원천세 신고·납부는 지급 다음 달 10일, 지급명세서는 업종·소득에 따라 매월 말일 또는 반기 — **자료가 상충**하므로 앱은 일정을 단정하지 않고 "확인 필요" 안내만 한다.
5. **근로계약서는 이 서비스 밖**: 현장 출석 확인 후 업체가 실물 교부. 서비스에는 **지원서(+서명)와 합격서만** 있다. 근로계약서 템플릿·전자서명·보관 기능을 만들지 않는다(REQ-PC16). 단, 지원서·합격서 보관이 "근로계약 서류"로 오해되지 않도록 화면에 "근로계약서는 현장에서 별도 작성" 문구를 둔다.

## 4. 숨김 구조 (구현 지침)
- 테이블: `feature_flags`(code, enabled, needs_legal_review), `payout_batches`·`payout_batch_items`, `settlements` 확장(paid_by, holder_name_matched, payout_batch_id). 송금 "실행" 상태는 **스키마에 존재하지 않는다**(T16).
- 서버: 플래그 OFF 이면 해당 API 는 **404**(존재를 드러내지 않음), 응답 `GET /features` 에서 false. 클라이언트는 이 값으로 메뉴/버튼을 숨긴다(UI 숨김만으로 보안 처리 ✕ — 반드시 서버에서 검사).
- 켜는 절차: ① 법무·세무 확인 기록 ② 은행 양식 확보(C) ③ ADMIN 의 `FLAG_MANAGE` 로 변경 + `confirmLegal` + 감사 로그 ④ 해당 업체 1곳 시범.
- 계좌 번호: 평문 저장·로그 ✕. 이체 파일 생성 순간에만 복호화, 배치 항목에는 끝 4자리만 남긴다. 파일은 비밀번호 보호 xlsx, 다운로드 감사.
- 지급 확인: "업체가 지급했다고 기록"한 것이지 플랫폼이 지급을 보증하지 않는다. 출연자 앱에는 "업체가 지급 완료로 기록" 상태 표시와 이의 제기(`DISPUTED`)만 제공(플래그 ON 시).

## 5. 사용자(업체 운영자)가 확인할 일
1. 세무사: 출연자 소득을 3.3% 사업소득/일용근로 중 무엇으로 처리하는지(현재 업체의 기존 방식 유지가 현실적).
2. 노무사: 근로자성 위험과 계약서 구조.
3. 변호사/금융 전문가: 이체 파일 생성이 "자금 이동 관여"에 해당하지 않는지, 개인정보(계좌·주민번호) 위탁 구조.
4. 은행: 기업뱅킹 대량이체 양식(추후).
5. 결과를 `docs/16` 에 기록하고 플래그를 켠다.
