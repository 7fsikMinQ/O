# 32. 권한 · API 보안 설계 (v1, 2026-11-19) — "API 주소만 알아도 조회·수정이 안 되게"

> 요구(사용자): 가입 승인 후 **권한별로** 기능이 열리고, **API 주소를 알아도** 권한 없이는 조회·수정이 안 되며, 필터·인터셉터·AOP 로 **API 별 권한**을 걸고, **직급·권한은 관리자 화면에서 등록·추가·수정**하며, 삭제는 **관리자·윗 직급만** 한다. 지금은 **관리자는 모든 것이 되고 관리자로 시험**한다.
> 상위 설계는 [31번](./31_OIO_통합플랫폼_구상.md), 화면은 [33번](./33_UI_디자인_시스템_v2.md). **확정/제안 구분**: 이 문서의 구조는 제안이며 사용자 확인 후 구현한다(관리자 전권·직급 화면·API별 권한은 사용자 확정).

## 1. 지금 코드의 보안 상태 (실제 점검 결과, 2026-11-19)
| # | 발견 | 위험 | 조치 |
|---|---|---|---|
| 1 | 권한이 **URL 규칙 2종**(`/admin/**`=관리자, 출연자 경로=ACTOR)뿐이고, 나머지는 `anyRequest().authenticated()` | 로그인만 되면 **어떤 사용자든** 해당 경로에 닿는다. 업체 경로는 서비스 안의 `CompanyAccess.require(...)`(약 52곳)가 막고 있어 **그 호출을 빠뜨린 새 API 는 곧바로 뚫린다** | **기본 거부(default-deny)**: 권한 표시가 없는 API 는 시작 시점에 실패(§4) |
| 2 | 직책 묶음이 `Roles.java` 의 **고정 Set**(OWNER/MANAGER/…) | 직급 추가·권한 수정을 화면에서 못 함 | 권한 항목(DB) 기반으로 교체(§3) |
| 3 | `/files/*` GET, `/jobs*` GET 등 공개 경로가 URL 패턴으로만 열려 있음 | 새 경로를 만들면서 패턴이 넓어지면 공개가 늘어남 | 공개 API 도 `@Public` 로 **명시**하고 목록을 시험으로 고정(§4) |
| 4 | Swagger(`/v3/api-docs`)는 개발에서 공개, 운영은 설정으로 끔 | 운영에서 켜지면 API 지도 노출 | 운영 프로파일에서 끔을 **시험으로 보증** |
| 5 | 객체 단위 검사(남의 데이터 접근)가 서비스마다 다름 | 일부 누락 가능 | "내 것/내 회사 것" 검사를 공통 함수로 모으고 **부정 시험**(타인 ID 로 요청 → 404/403)을 엔드포인트마다 둠 |
| 6 | 권한이 JWT `roles` 에 **굳어 있음**(15분) | 직급을 바꿔도 최대 15분 옛 권한 유지 | 권한은 **요청 때 DB(짧은 캐시 ≤30초)로 확인**, 직급 변경·정지 시 캐시 무효화 |

## 2. 모델: 누가 → 어떤 직급 → 어떤 권한 → 어떤 API
```
user ─(소속)→ staff_member ─(직급)→ staff_position(서열 rank) ─(묶음)→ position_permissions ─→ permission(코드)
                       └─(개별 가감)→ member_permission_overrides (예외 허용/차단, 선택)
API 메서드 ──(@RequirePermission("코드"))──▶ permission
```
- **총괄·관리자(ADMIN/SUPER_ADMIN)**: 모든 권한을 자동 보유(`*`). 시험은 이 계정으로 한다.
- **직급(staff_position)**: 이름·서열(rank, 큰 수가 상위)·설명·활성 여부. **관리자가 화면에서 추가·수정·비활성화**한다. 삭제는 쓰는 사람이 없을 때만 가능(그 외 비활성).
- **권한 항목(permission)**: 코드·이름·그룹. 코드는 **개발이 정의**(API 에 붙는 값)하고, 직급에 어떤 코드를 줄지는 **관리자가 화면에서 고른다**.
- **직급에 소속 + 기능 권한 묶음**: 스케줄러처럼 "직급과 별개로 붙는 기능"은 **권한 묶음(role)** 로 만들어 사람에게 추가 부여한다(직급 1개 + 묶음 여러 개).
- **서열 규칙**: 같거나 높은 서열의 사람의 직급·권한·삭제·승인을 **바꿀 수 없다**(자기보다 낮은 서열만). 자기 자신의 권한을 올릴 수 없다. 관리자는 예외.

### 2-1. 권한 항목 목록 (초안 — 단계 1 기준, 확장 가능)
| 그룹 | 코드 | 설명 |
|---|---|---|
| 일정 | `SCHEDULE_READ` / `SCHEDULE_WRITE` / `SCHEDULE_PUBLISH` / `SCHEDULE_DELETE` | 열람 / 등록·수정 / 공개·마감 / 삭제(숨김) |
| 필요 인원 | `HEADCOUNT_WRITE` | 필요 인원(유형·요건·정원) 수정 |
| 팀장 | `LEADER_SELF` / `LEADER_ASSIGN` / `LEADER_EDIT` / `LEADER_REMOVE` | 본인 등록·취소 / 타인 등록 / 수정 / 삭제 |
| 선발 | `APPLICANT_READ` / `SELECT_DECIDE` / `SELECT_RECOMMEND` | 신청자 열람 / 합격 통보 / 추천 |
| 인재 DB (3단계) | `TALENT_READ` / `TALENT_WRITE` / `TALENT_MEDIA_READ` / `TALENT_SENSITIVE_READ` | 열람 / 수정 / 영상·이력서 열람 / 주민번호 등 전체 열람 |
| 현장 | `FIELD_ROSTER` / `FIELD_ATTEND` / `FIELD_BROADCAST` | 인원표 / 출결 체크 / 단체 알림 |
| 직원 관리 | `STAFF_APPROVE` / `STAFF_POSITION_ASSIGN` / `STAFF_SUSPEND` | 가입 승인 / 직급 부여 / 정지 |
| 직급·권한 관리 | `POSITION_MANAGE` / `PERMISSION_MANAGE` | 직급 추가·수정 / 권한 묶음 수정 |
| 삭제·복구 | `RECORD_DELETE` / `RECORD_RESTORE` | 삭제(숨김) / 복구 |
| 시스템 | `AUDIT_READ` / `SETTINGS_WRITE` / `CONSENT_TERMS_MANAGE` | 감사 로그 / 설정 / 약관·동의서 관리 |
| 외부 제공 (4단계) | `BUYER_MANAGE` / `DATASET_EXPORT` | 구매자 관리 / 데이터 반출 |
초기 직급별 묶음(제안값, 관리자가 바꿈)은 31번 §2-2 표를 따른다. **삭제 계열(`RECORD_DELETE`)은 대표·이사·관리자에게만 기본 부여**하고 그 아래 직급에는 부여하지 않는다(사용자 확정: 삭제는 관리자·윗 직급).

## 3. DB (제안)
| 테이블 | 핵심 컬럼 |
|---|---|
| `staff_positions` | id, name, rank(INT, 큰 수=상위), description, is_active, is_system(관리자·대표 등 삭제 불가 표시) |
| `permissions` (기존 확장) | code, name, group_name, is_sensitive |
| `position_permissions` | position_id, permission_id |
| `staff_roles` / `staff_role_permissions` | 기능 묶음(예: 스케줄러) |
| `company_members` (확장) | position_id, `status`(PENDING/ACTIVE/SUSPENDED/REJECTED), approved_by, approved_at, request_note |
| `member_roles` | member_id, staff_role_id |
| `member_permission_overrides` | member_id, permission_id, effect(ALLOW/DENY), reason, by_user (선택 기능) |
| `permission_audit` (감사 로그 재사용) | 모든 직급·권한 변경 기록(누가·무엇을·전→후) |
- **삭제는 소프트**: 각 업무 테이블에 `deleted_at`, `deleted_by`, `delete_reason`. 목록 기본 조건에 `deleted_at IS NULL`. 복구는 `RECORD_RESTORE`.
- 기존 `member_role` CHECK(OWNER/MANAGER/…) 는 마이그레이션 V1 재생성(첫 운영 배포 전)으로 `position_id` 로 대체하고 시드(대표·이사·현장 실장·캐스팅 매니저·현장 팀장·직원, 기능 묶음 스케줄러)를 넣는다.

## 4. 강제 장치 (5겹)
| 겹 | 장치 | 하는 일 |
|---|---|---|
| ① 인증 | Spring Security 필터(JWT) | 토큰 없음/만료 → 401. 승인 대기·정지 계정은 토큰이 있어도 **403(`ACCOUNT_NOT_ACTIVE`)** |
| ② **API 권한 선언** | `@RequirePermission("SCHEDULE_WRITE")`(메서드) / `@Public`(공개 명시) / `@AnyStaff`(로그인한 직원) | **모든 API 는 이 셋 중 하나가 반드시 있어야 한다** |
| ③ **중앙 검사(인터셉터/AOP)** | `PermissionInterceptor`(HandlerInterceptor, 컨트롤러 진입 전) | 요청한 사람의 권한을 `PermissionService`(DB, ≤30초 캐시)에서 조회 → 없으면 **403**, 모든 거절은 감사 로그(누가·어느 API·어떤 권한 없음) |
| ④ 객체 단위 | `ScopeGuard`(공통) | "내 회사/내가 배정된 일정/내 데이터" 인지 확인. 남의 ID 면 **404**(존재 노출 안 함) |
| ⑤ DB 제약 | 외래키·체크·유니크·(필요 시 RLS) | 앱 버그가 있어도 정원·겹침·유니크는 DB 가 막음(기존 방식 유지) |
**서열 검사**(상위만 하위 변경·삭제)는 ③에서 권한 코드 + `RankPolicy` 로 확인한다.

### 4-1. "선언 누락" 자동 차단
- **시작 시 검사**: 스프링이 알고 있는 모든 컨트롤러 메서드를 훑어, `@RequirePermission`·`@Public`·`@AnyStaff` 중 하나도 없으면 **서버가 켜지지 않는다**(운영) / 시험이 실패한다.
- **API 권한 지도 시험(`ApiPermissionMapTest`)**: (메서드+경로 → 권한 코드) 전체 목록을 만들어 **기준 파일(`docs/api-permissions.csv`)과 비교**한다. 새 API 를 만들면 기준 파일도 같이 고쳐야 통과 → 리뷰에서 권한이 눈에 보인다. 이 CSV 는 문서 생성기가 08번 API 명세에 "필요 권한" 열로 싣는다.
- **존재하지 않는 권한 코드** 사용 시 시작 실패.

### 4-2. 부정 시험 (필수, 엔드포인트마다)
각 보호 API 에 대해 자동으로 다음을 요청해 **거절되는지** 본다(`PermissionNegativeIT`, 파라미터화):
1. 토큰 없음 → 401  2. 승인 대기 직원 → 403  3. 권한 없는 직급 → 403  4. 출연자 토큰으로 직원 API → 403  5. 다른 회사/남의 ID → 404  6. 만료·변조 토큰 → 401  7. **권한 회수 직후**(캐시 무효화) 즉시 403  8. 서열이 같거나 높은 사람 변경·삭제 시도 → 403.

### 4-3. 공통 방어
| 항목 | 내용 |
|---|---|
| 응답 | 권한 없음은 403, 존재 노출을 피할 객체 접근은 404. 메시지에 내부 정보 ✕ |
| 속도 제한 | 로그인·가입 신청·인증번호·파일 업로드·권한 거절 반복 시 제한(기존 로그인 잠금 방식 확장), 접속 제한 대신 **계정 승인제와 속도 제한**으로 방어 |
| 입력 | 모든 요청 DTO 검증(`@Valid`), 크기 제한(기존 5MB), 파일 형식 실내용 검사 |
| 쓰기 | 상태를 바꾸는 API 는 **감사 로그**(누가·무엇·전후) 필수 |
| 로그 | 토큰·주민번호·계좌·영상 URL 서명값 ✕ |
| 헤더 | HSTS(있음), `X-Content-Type-Options`, `Referrer-Policy`, CSP(웹) 추가 |
| 접속 제한 | **없음**(사용자 결정). 대신 대표·이사·관리자 계정은 **TOTP 2차 인증**을 운영 전 적용(직원 개인정보 접근 권한이므로) |

## 5. 가입·승인 흐름 (직원)
```
직원 가입 신청(이름·이메일·연락처·희망 직급 메모)
  → 이메일 확인(링크) → 상태 PENDING(승인 대기, 로그인은 되지만 아무 API 도 안 열림)
  → 승인 권한자(대표·이사·관리자 등 STAFF_APPROVE)가 승인 + 직급 부여 → ACTIVE
  → 반려(사유) / 정지(사유)
```
- 승인 권한자가 **자기 서열 이상 직급을 부여할 수 없다**. 승인 대기 사람 목록은 승인 권한자에게만 보이고, 승인·반려 알림 메일을 보낸다.
- 스팸 방지: 이메일 확인 필수, 같은 IP 가입 신청 속도 제한(시간당 5건), 미확인 신청은 24시간 뒤 자동 삭제.

## 6. 관리자 화면 (직급·권한 관리) — 단계 1 필수
| 화면 | 기능 |
|---|---|
| 직원 목록 | 상태(승인 대기/활성/정지)·직급·기능 묶음, 검색, 승인·반려·정지·직급 변경(서열 규칙 적용) |
| 승인 대기 | 신청자 정보·메모, 직급 선택 후 승인, 반려 사유 선택지+기타 |
| **직급 관리** | 직급 추가·이름·서열 변경(드래그 또는 숫자)·설명·비활성, 사용 인원 수 표시 |
| **권한 관리** | 직급(또는 기능 묶음)을 고르면 권한 코드가 그룹별 체크박스로 나오고 저장. **민감 권한은 경고 표시**. 변경 전·후 미리보기, 저장 시 사유 입력 |
| 권한 시험 도구 | "이 직원이 이 API 를 호출할 수 있나?"를 사람·API 로 조회(관리자 전용, 개발·운영 모두) |
| 감사 로그 | 누가 무엇을 언제 바꿨는지 검색, 거절 기록 포함 |
| 휴지통 | 삭제된 항목 목록·복구(`RECORD_RESTORE`) |
- 직급·권한은 **화면에서 전부 바꿀 수 있어야 하므로 코드에는 권한 코드와 "초기값(시드)"만** 둔다.

## 7. 삭제 정책 (사용자 확정: 삭제는 관리자·윗 직급)
- 일반 직원·팀장·캐스팅 매니저 등은 **삭제 버튼이 없다**. 대신 **취소·숨김(사유 필수)** 만 가능.
- 삭제 권한(`RECORD_DELETE`)은 대표·이사·관리자에게 기본 부여, 서열이 낮은 사람이 만든 것만 지울 수 있다(관리자는 전부).
- **예외(법적 권리)**: 출연자 본인의 **개인정보 삭제·동의 철회 요구**는 직급과 무관하게 **본인이 직접** 할 수 있어야 한다(개인정보 열람·정정·삭제·처리정지 요구권, ◐ 확인). 처리는 기한 내 이행하고 감사 기록을 남긴다.
- 삭제된 데이터의 **물리 파기** 기한(보존기간 경과)은 설정값으로 두고 배치로 처리, 증빙(지원서·출결)은 보존기간 정책을 따른다.

## 8. 구현 순서 (단계 1 안)
1. DB: `staff_positions`·`position_permissions`·권한 시드·`company_members` 확장, V1 재생성, 스키마 시험 보강.
2. 권한 프레임워크: 애노테이션·`PermissionInterceptor`·`PermissionService`·`RankPolicy`·`ScopeGuard`, 시작 시 검사, `ApiPermissionMapTest`, 기준 CSV 생성.
3. 기존 약 136개 API 에 권한 선언을 붙이고(출연자 API 는 `ROLE_ACTOR` 전용 선언), 기존 `Roles.java` 사용처 교체, 기존 시험을 새 권한 기반으로 이전.
4. 직원 가입·승인·직급 부여 API + 관리자 화면(§6).
5. 부정 시험 `PermissionNegativeIT`, 속도 제한, 감사 로그 연결.
6. 삭제·복구(소프트) 공통 처리.

## 9. 배포 분리 시 보안 추가 (31번 §10, 제안)
직원용(`staff-api`)과 출연자용(`actor-api`)을 별도 실행 프로그램으로 나누면 **API 권한 5겹에 한 겹이 더해진다.**
| 항목 | 내용 |
|---|---|
| 토큰 | 발급자·서명 키·audience 분리. `staff-api` 는 직원 토큰만, `actor-api` 는 출연자 토큰만 받는다(교차 사용 시 401) |
| DB 계정 | `actor_app` 은 출연자 영역만 GRANT. 직급·권한·감사·구매자·반출 테이블은 접근 불가 → 출연자용이 뚫려도 직원용 데이터에 닿지 못함 |
| 시험 | 부정 시험에 **교차 토큰**(출연자 토큰→직원 API, 직원 토큰→출연자 API)과 **DB 권한 시험**(`actor_app` 으로 직원 테이블 조회 시 거절)을 추가 |
| 공개 API | 출연자용의 공개 경로(공고 목록 등)는 조회용 뷰만 사용 |
